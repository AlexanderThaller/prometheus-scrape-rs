= Performance improvements, round 4
:toc:
:source-highlighter: rouge

Tracking document for the fourth optimization round (2026-07-13, branch
`perf-improvements-3`). Round 3 (see `perf-improvements-2.adoc`) shipped the
single-pass RW2.0 encoder, `Bytes` body fetch, precomputed label hashes and
the single-sample series type; production confirmed −19% CPU per replica.
Memory savings still outrank CPU savings; nothing in this round may grow
per-series retained state.

* `python3 -m http.server 18000` serving `pgo-corpus/*.prom`;
* one job per corpus file × two replica-labeled targets (14 targets,
  30,586 tracked series), `scrape_interval: 4s`;
* `remote_write` straight to the NAS Mimir
  (`http://192.168.1.94:9009/api/v1/push`,
  `protobuf_message: io.prometheus.write.v2.Request`,
  `X-Scope-OrgID: anonymous`).

clean throughout every capture: zero retries, zero failed batches, zero
dropped series.

Profiling binary: `--profile profiling` with
`RUSTFLAGS="-C force-frame-pointers=yes"`.

== Candidates

=== 1. Stop recompressing the retained body when the series set is unchanged

Target: *−6.3% total live CPU* (the `advance` → `compress_vec` block),
zero RSS change. File: `src/scrape.rs`.

`SeriesTracker::advance` snappy-compresses the full scrape body *every
scrape*, but the retained body exists only to re-derive label sets of
*vanished* series. When the current scrape's (sorted) hash set equals the
tracker's previous one — the overwhelmingly common steady state — the old
retained body can answer every future re-derivation the new one could:
label sets per identity are deterministic and value/timestamp changes are
irrelevant to markers. Keep `RetainedScrape.start_ms` as the *retained
body's* scrape time (the re-parse filter must keep using it), and replace
the body only when the hash set changed (or nothing is retained yet).

Caveat to verify: a series with an *explicit* exposition timestamp that
happens to equal the retained body's `start_ms` — same edge as today,
covered by existing tests.

=== 2. Series identity from the raw exposition line, hashed during parse

Target: the *11.4%* `hash_labels_into` block (minus a small replacement
cost in the parser, where the bytes are already in L1). Files:
`src/parser.rs`, `src/scrape.rs`, `src/model.rs`.

The staleness identity only has to be (a) stable across scrapes and
(b) re-derivable from the retained body. Both hold for a hash of the raw
identity bytes of the exposition line (metric name through closing `}`),
computed *in the parser* over one contiguous, cache-hot slice — instead
of re-hashing ~15 finalized `CompactString`s per series per scrape
through a serial-multiply chain. `finalize_series_labels` stops hashing
entirely; re-derivation matches vanished raw-hashes against the re-parse
of the retained body (which reproduces identical raw lines by
construction), then finalizes labels only for the vanished ones.

Semantic shift (same trade Prometheus' scrape cache makes — it keys
series on the raw metric string too): if an exporter changes the *textual
form* of a series without changing its labels (label reordering,
whitespace), the tracker sees one identity vanish and one appear — one
spurious staleness marker racing one real sample at the same timestamp.
Bounded, self-healing, and only on a formatting change between two
scrapes of the same target.

Also fixes silently-dead work found while reading: `stale_series` hashes
its marker labels, but markers are appended to the batch *after*
`tracker.advance` ran — nothing ever reads that hash.

Fallback if the semantics are rejected: break the FxHash dependency chain
instead (two/four independent lanes folded at the end, ~16–32 B per
round). The annotation says latency, not throughput, is the limit, so
expect roughly a 2–3× reduction of the 11.4% rather than elimination.

=== 3. Right-size the parser's label Vec — status: *rejected after attribution*

The 88% site's original reading ("`with_capacity(12)` plus a growth
realloc") was wrong. Measured against the corpus (2026-07-13): the
maximum exposition label count is 9 + name = 10, so with three target
labels the capacity-12 Vec suffices for ~97% of series — the realloc is
negligible. The heaptrack entry merges two inlined per-series
allocations instead:

* 1.0/series — the label `Vec` itself (the floor of the owned-label
  model);
* ~0.93/series — the *metric-name* `CompactString` heap spill: 93% of
  corpus series have names longer than the 24-byte inline buffer, and
  the name is re-allocated for every series on every scrape. (The
  separately listed compact_str site, 367 k calls, is the label-*value*
  spills at 0.21/series plus rare long label names.)

No cheap fix exists inside the current model: `Label` stays 48 bytes
(pinned), `CompactString` clones of heap strings allocate, and a
`SmallVec<[Label; 8]>` would trade the alloc for 384 B of extra memcpy
per series move (alloc ~7% vs libc memcpy ~6% — a wash at best). The
real lever remains the batch-level arena (deferred, below).

=== 4. Encoder pass-1 packed-length accumulation

Target: part of the 10.0% flush-closure block. File:
`src/remote_write.rs`.

The write loop re-walks every series' refs summing `varint_len` to size
the packed field. Pass 1 already touches every ref as it pushes —
accumulate per-series packed length there (one `u32` per series in
`V2Scratch`) and the write loop stops re-deriving it. Expect ~1–2%, may
also help `intern` cache behavior slightly.

=== 5. Tracker micro-allocations

Reuse a per-tracker `Vec<u64>` for `current` (today: collect + sort +
drop per scrape per target) and a scratch for `vanished`. Purely
mechanical, rides along with candidate 1's edit. Sub-1% CPU, small
steady allocation-rate cut.

=== Deferred / rejected

* *Retain the raw body instead of compressing* — kills the whole 6.3%
  but costs ~7× retained-body RSS per target; memory priority says no.
  Candidate 1 gets most of the win for free.
* *Per-target cache of finalized label sets keyed on raw lines*
  (Prometheus scrape-cache style, would also kill `finalize` +
  `sort_labels`) — reintroduces ~500 B/series retained state, the exact
  thing the vmagent-style tracker was built to avoid (~160 MiB at the
  production replica's 322k series). Rejected on RSS.
* *Batch-level label arena* (one allocation per scrape instead of one
  per series) — would eliminate most of the 88% site, but `TimeSeries`
  would carry arena ranges through relabeling/sorting/encoding; too
  invasive for this round, revisit if candidate 3 lands short.
* *Wider `Label` inline buffer* for the 10% CompactString spills —
  `Label` must stay 48 bytes (pinned by test since the bytes-labels
  regression); no room.
* *Payload snappy (3.66%)* — protocol-mandated, already raw-format.
